# Secure AI Architecture
February 7, 2026

One topic that has been on the top of my mind, and probably many others, in recent months has been AI Security. More specifically, I have been pondering the question of "how can I connect an AI system to things without compromising on security"? To answer this question it is worth defining an "AI Security Doctrine" to help guide the creation of a secure AI architecture.

## AI Security Doctrine
An AI system should never be given unsupervised access to API keys or other systems that could be used by the AI system to modify data. Rather, an AI Agent deployed within a given domain should utilize "Skills", reusable instructions, that are loaded on demand and used to perform repeatable tasks.

## AI Security Core Principles
1.  **Zero Trust for AI:** AI models never handle raw authentication tokens.
2.  **Proxy Isolation:** All tool execution is routed through a controlled gateway.
3.  **Data Pruning:** Responses are stripped of sensitive metadata before reaching the AI context.
4.  **Network Lockdown:** Infrastructure operates within a private VPC with strict Security Group egress rules.

## Secure AI Architecture
This architectural model is based off of using the terminal-based open source AI coding agent, [opencode](https://opencode.ai/). This model utilizes several concepts that are part of the opencode ecosystem such as [Agents](https://opencode.ai/docs/agents/) and [Skills](https://opencode.ai/docs/skills/). Combined with a separate API Server, Agents and Skills can be configured to allow AI infrastructure to safely access proprietary data in a secure environment.

![secure ai architecture diagram](/images/secure-ai-architecture/scng-ai-framework.png)

1. **AI Server:** The brain that requests actions (e.g., "Read Jira Ticket"). There are no credentials stored on this system, only Skills that the AI model can use to interact wit the API Server.
2. **API Server:** The secure server that holds the API keys, validates the requests from the AI Server, and calls the external services (Jira, GitHub, Slack, etc...).
3. **External APIs:** The actual services (Jira, GitHub, etc.) that are never directly accessed by the AI Server.

### Why Use Skills?
Skills decouple intent from execution. By abstracting capabilities into defined "Skills" (simple Markdown or Python definitions), the AI system is forced to operate within a bounded context.

- **Determinism:** Instead of letting an AI system hallucinate complex API requests, a Skill forces it to output a predictable structured command.

- **Auditability:** Skills create a clear log of intent. It is far easier to audit "The AI requested the jira-read skill" than to parse a raw HTTP request generated by an LLM.

- **Modularity:** Skills can be hot-swapped. If a security vulnerability is found in the code that is used to access Jira for example, the single Skill definition can be patched. This would instantly patch every AI agent using the Skill without retraining or re-prompting the models. It also allows for a user to change the model they are using without altering the Skill.

### The "Zero-Knowledge" Principle for Secrets

AI models are probabilistic engines, not secure vaults. There is a non-zero risk of "Prompt Injection" attacks where an external actor tricks the AI into revealing its system instructions or context.

- **Credential Isolation:** If an AI system holds an API key in its system prompt or memory, a successful injection attack could leak that key to a malicious user.

- **The Proxy Solution:** By using a "Tool Proxy" architecture, the AI never sees the API key. It only sees a "door" (the endpoint). If the AI system is compromised, the attacker finds a door they cannot open because the key resides firmly on a separate, locked-down server the AI cannot access directly.

### Benefits of Controlled Execution

Direct API access grants an AI the same permissions as the API key it uses—often far more than necessary. Using a proxy to control API calls creates a crucial layer of "Data Governance."

- **Scope Restriction:** For example, a raw Jira API token might allow reading, writing, and deleting all tickets. A controlled Skill can restrict the AI to only GET /issue requests, physically preventing it from deleting data even if it "wants" to.

- **Data Pruning & Privacy:** External APIs often return massive JSON blobs containing sensitive metadata (user emails, internal IP addresses). A controlled proxy filters this noise, ensuring the AI only receives the data it needs to answer the question, keeping the compliance footprint minimal.

- **Rate Limiting & Cost Control:** A runaway AI loop could make thousands of expensive API calls in seconds. A proxy layer allows a user to implement rate limits that are impossible to enforce inside the LLM itself.

## Conclusion
As AI systems become more capable, it is increasingly challenging to integrate them with external tools in ways that are both useful and secure. Additionally, private organizations face mounting pressure to deploy AI systems wherever possible. This pressure often leads to rushed deployments that pose organization-wide security risks. Therefore, establishing robust governance, validation, and security controls is critical to maintaining organizational resilience in AI-enabled environments.
